**Status: ✅ DONE — two-phase approach implemented, venue_archetypes removed, district coverage check added, 652/652 tests passing**
**Blocks: nothing (quality improvement — must run before next city generation)**

## The problem

`research_city.py` makes a single LLM call to generate the entire city config from scratch,
including geographically-sensitive fields like `districts`, `centre_lat/lng`, and `radius_km`.
Because it has no grounding, the LLM produces plausible-sounding but unreliable outputs:

- London's district list contained 0 venues in Westminster, City of London, or Kensington
  because those districts were simply never listed — the LLM anchored on the food/arts circuit.
- `centre_lat/lng` is mostly correct for major cities but unreliable for smaller or
  less-famous ones.
- The `districts` list is the single biggest driver of venue geographic coverage, so any
  LLM hallucination here propagates through every venue generated for that city.

Only two fields genuinely require LLM cultural knowledge and have no open-data equivalent:
`local_cuisine_label` and `cuisine_variety`. Everything else can be fetched deterministically
or is already generated by a better mechanism elsewhere.

---

## What happens to venue_archetypes

`venue_archetypes` (20 food descriptions + 20 sight descriptions) is removed entirely from
this call and from `city_config`. The reasoning:

- **High-traffic iconic venues** are already handled by the planning prompt's tier
  description: "Think: Central Park / Statue of Liberty for New York — apply the same
  standard for {city}." The LLM doesn't need 20 examples to understand what globally
  recognisable means; the tier description handles this directly.
- **Mid/low tier inspiration** is what archetypes were actually good for, but `city_interests`
  already covers this role — "History & royal heritage, Multicultural food markets, Parks &
  green spaces" gives the planning call the same cultural flavour signal with far less
  prompt bulk.

`city_interests` is already generated by `generate_city_interests()` (a separate LLM call)
and is injected into the event generation call. It should also be piped into the planning
call as a single-line cultural context line. No new LLM call needed.

---

## Impact

A city whose landmark districts are missing from the config will never generate venues in
those areas, because the planning prompt limits venues to listed districts. The fix is
upstream: get the districts right before generation starts.

---

## Design

Replace the single monolithic LLM call with a two-phase approach:

**Phase 1 — Open data fetch (no LLM)**
1. Nominatim lookup: city name → `centre_lat`, `centre_lng`, `display_name`, `country`
2. Overpass query: admin-level subareas within the city bounding box → `districts`
3. Radius calculation: derived from the city's OSM admin boundary polygon extent
4. Open-Meteo API: historical climatology for the task date range → `weather_notes`
5. Calendar arithmetic: compute `task_dates` (next Saturday 2-3 months out)

**Phase 2 — Focused LLM call (2 fields only)**
Prompt asks for:
- `local_cuisine_label` — dominant local cuisine (e.g. "british", "japanese")
- `cuisine_variety` — 10-12 cuisine types present in the city's food scene

The Phase 2 prompt receives `display_name`, `country`, and `districts` from Phase 1 as
context, but does not ask for `venue_archetypes`.

**Planning prompt change (in generate_city_venues.py)**
Remove the `archetype_block` injection entirely. Replace it with a single line derived
from `city_interests`:
```
Visitor interests: {city_interests_joined}
```
`city_interests` is generated by `generate_city_interests()` earlier in the pipeline
(or falls back to the hardcoded `_LONDON_DEFAULT_INTERESTS` / `_TOKYO_DEFAULT_INTERESTS`).
This gives the planning LLM the same cultural flavour signal with ~5 tokens instead of
~800 tokens of archetype descriptions.

## Open data sources

| Field | Source | API | Notes |
|---|---|---|---|
| `centre_lat`, `centre_lng`, `display_name`, `country` | Nominatim (OSM) | `nominatim.openstreetmap.org/search` | Free, 1 req/sec rate limit |
| `districts` | Overpass (OSM) | `overpass-api.de/api/interpreter` | Query admin_level 8-10 subareas |
| `radius_km` | Derived from OSM boundary | Same Overpass call | Compute from bbox of the boundary polygon |
| `weather_notes` | Open-Meteo | `api.open-meteo.com/v1/climate` | Free, no key, daily historical means |
| `task_dates` | Calendar arithmetic | — | Next Saturday 2-3 months out |
| `local_cuisine_label`, `cuisine_variety` | LLM | Same as now | DeepSeek or Claude |

## Tasks

- [ ] **Add `_fetch_city_geodata(city_name) → dict` in `research_city.py`.**
  Calls Nominatim for coordinates and admin name, then Overpass for subareas.
  Returns `{centre_lat, centre_lng, display_name, country, districts, radius_km}`.

  Overpass query pattern:
  ```
  [out:json][timeout:30];
  area["name"="{display_name}"]["admin_level"~"^[46]$"]->.city_area;
  (
    relation(area.city_area)["admin_level"~"^(8|9|10)$"]["name"];
    node(area.city_area)["place"~"^(suburb|quarter|neighbourhood)$"]["name"];
  );
  out tags;
  ```
  Deduplicate by name. Filter out entries whose names are clearly not neighbourhoods
  (e.g. numeric-only names, single characters). Sort alphabetically. Cap at 20 results.
  If fewer than 6 results, fall back to LLM generation for districts only.

- [ ] **Add `_fetch_weather_notes(lat, lng, task_dates) → str` in `research_city.py`.**
  Calls Open-Meteo historical climate API:
  ```
  GET https://climate-api.open-meteo.com/v1/climate
      ?latitude={lat}&longitude={lng}
      &start_date={task_dates[0]}&end_date={task_dates[-1]}
      &models=EC_Earth3P_HR
      &daily=temperature_2m_mean,precipitation_sum
  ```
  Summarises as a single natural-language string: "June in London: avg 17°C, occasional
  light rain." Returns a generic fallback string if the API is unreachable.

- [ ] **Add `_compute_task_dates() → list[str]` in `research_city.py`.**
  Returns 6 consecutive dates starting on the next Saturday that is 8-12 weeks out from
  today's date. No external call needed.

- [ ] **Rewrite `research_city()` to use two-phase approach.**
  - Call `_fetch_city_geodata()` first.
  - If geodata fetch succeeds: pass those fields directly into `_save_config()`, skip
    them in the LLM prompt.
  - If geodata fetch fails (network timeout, city not found): fall back to LLM for all
    fields, log a warning. Existing fallback behaviour preserved.
  - Trim RESEARCH_PROMPT to only ask for `local_cuisine_label` and `cuisine_variety`.

- [ ] **Rewrite RESEARCH_PROMPT to 2-field output.**
  Remove all fields now fetched from APIs. Remove `venue_archetypes` entirely.

- [ ] **Remove `venue_archetypes` from `_save_config()` and all config references.**
  The field was never stored in the city_config DB table — it lived only in the
