# E2.5 — Agent-Loop Task Generation
**Status: ✅ complete**
**Depends on: E2 (lat/lng in pool, load_ground_truth DB, unavailable_dates)**
**Blocks: E3 (gate enforcement is more meaningful with better input quality)**

---

## Problem

Task generation is currently single-shot: one LLM call returns the full task JSON.
The model simultaneously reasons about venue pool geometry, constraint calibration,
feasibility, and JSON schema — all in one forward pass. It defaults to plausible-looking
constraints without actually stress-testing them. This is the primary reason generated
tasks aren't as hard as intended.

---

## Design: Full Agent Loop

Replace `_call_single_task_llm` with a full agent loop. The agent uses tools to explore
the pool freely, reasons about feasibility, then calls SUBMIT with the final task JSON.
SUBMIT runs the existing validation pipeline — the loop only terminates when the task
passes validation cleanly.

**No two-phase handoff.** One loop, one output. The agent decides when it's ready.

---

## Tools (6 total)

### HELP(query)
Handbook queries. Lists available tools, explains schemas, lists all valid field values
(tags, regulations, traffic tiers, price tiers, categories, pace values).
Handbook content is **dynamically generated** at loop-start from actual pool data:
- All distinct tags for this city (queried from DB)
- All regulation fields with valid values
- All categorical field values (traffic_tier, price_tier, recommended_pace, category, noise_level)
- A sample venue showing all fields returned by get_venue

### query_pool(filters)
Returns `[{venue_id, name}]` — names only, no detail.
Agent uses this to discover what exists, then calls get_venue for specifics.

**Filter dict (AND logic — all conditions must match):**
```json
{
  "category": "bar",
  "tag": "halal",
  "regulation": "wheelchair_accessible",
  "district": "Shoreditch",
  "traffic_tier": "low",
  "price_tier": "budget",
  "booking_required": true
}
```
Any subset of fields. All conditions are AND. Single-field calls are fine.
For tag and regulation filters: venue must have that tag / that regulation = true.
Returns empty list if nothing matches — this is useful information (intersection is empty).

### get_venue(venue_id)
Returns full venue data:
```json
{
  "venue_id": "lon_r01",
  "name": "...",
  "category": "restaurant",
  "district": "Shoreditch",
  "traffic_tier": "mid",
  "recommended_pace": "moderate",
  "price_tier": "mid",
  "avg_cost_local": 28.0,
  "lat": 51.522,
  "lng": -0.077,
  "recommended_visit_minutes": 90,
  "tags": ["italian", "vegetarian-options", "locals-favourite"],
  "regulations": {
    "wheelchair_accessible": true,
    "pet_friendly": false,
    "noise_level": "moderate",
    "age_restriction": null,
    "dress_code": null,
    "photography_allowed": true,
    "family_friendly": true,
    "booking_required": false
  },
  "has_official_site": true,
  "booking_required": false,
  "window_flags": {},
  "unavailable_dates": ["2026-08-23"]
}
```

### estimate_travel(venue_id_a, venue_id_b, mode)
Haversine calculation for a specific pair.
mode: "walking" | "transit" | "cycling"
Returns: `{distance_km, walk_minutes, transit_minutes}`
Uses `haversine_km` + `estimate_minutes` from `build_travel_matrix.py`.
The agent only pays the cost for pairs it actually needs — no table injection.

### THINK(thought)
Log a reasoning step. Does not call the DB or any external service.
Use to record decisions, intermediate calculations, constraint choices.
Not required but strongly encouraged between tool calls.

### SUBMIT(task_json)
Attempt to finalise the task.

**Runs validation before terminating:**
1. JSON parse check — must be valid JSON
2. `validate_task_schema(task, pool)` — structural checks (required fields, hop-2 rule,
   constraint tension, source_in_profile, B-score completeness)
3. `_verify_task_solvable(task, pool)` — feasibility check (venue intersection,
   Type 2 geometry, pool coverage)

**On validation pass:** loop terminates, task returned to caller.

**On validation fail:** SUBMIT returns error details to the agent as a tool result.
The agent sees the exact validation messages and can fix the issues and try again.
The loop continues — SUBMIT does not terminate the loop on failure.

Loop terminates on: successful SUBMIT, or MAX_TURNS exhausted.

## Per-Type Reasoning Steps

These are injected into the system prompt as the required reasoning protocol for each
structural type. The agent must follow these steps before calling SUBMIT.

### Type 1 — Cascading Requirements
1. Decide persona: Cat 1 composition + Cat 7 occasion. Write the natural query signal
   for each.
2. For each signal, derive the constraint it implies. Every constraint must trace to
   something stated in the query — no invented constraints.
3. Use `query_pool` to check how many venues survive all constraints applied together.
   Is there still enough to build a schedule?
4. Confirm the constraints compound — they should narrow the pool from different angles,
   not all point at the same venues. If they all filter the same way, add a different
   dimension or change the persona.

### Type 2 — Subset Selection Under Time Ceiling
1. Decide the target subgroup: which category, any label or tier filter.
2. Use `query_pool` to find candidate venues in that subgroup.
3. Use `get_venue` to inspect promising candidates. Use `estimate_travel` to check
   distances between specific pairs you're considering.
4. Decide how many venues the agent must visit (minimum 3). Compute minimum time:
   sum of visit durations + travel between the nearest cluster you've identified.
5. Set the time ceiling so the nearest valid combo fits, but only just — the agent must
   pick wisely. Adjust ceiling or venue selection until: minimum_time < ceiling <
   minimum_time × 1.4. State the ceiling explicitly before calling SUBMIT.

### Type 3 — Competing Requirements
1. Decide the tension pair — two signals that pull at genuinely different parts of
   the pool (e.g. hidden-gem vs iconic, authentic-local vs famous-sights).
2. Use `query_pool` to enumerate each side separately. Check overlap: if most venues
   satisfy both constraints simultaneously, the tension isn't real — adjust.
3. Confirm there are enough venues on each side to fill the schedule. Neither side
   should dominate (rough guideline: 25-75% split).

### Type 4 — Precision Allocation
1. Decide a specific budget per day (a number, not a range).
2. Use `query_pool` + `get_venue` to find the cheapest valid plan: cheapest meal +
   cheapest site/activity satisfying all other constraints (free entry counts).
3. Verify: budget ceiling should be 1.5–1.75× the cheapest all-in day. This creates
   real allocation pressure without being impossible.
4. Add one "costly but justified" spend (the occasion or interest signal). Confirm:
   if the agent includes that spend, the rest of the day at cheapest-option cost still
   fits under budget. Target 1.1–1.3× floor after the costly spend is included.
5. Name the specific premium option that would blow the budget if the agent isn't careful.

### Type 5 — Hard Feasibility Reduction
1. Decide the constraint combination — at least 3 filters from different clusters
   (e.g. regulation + tag + district). Do NOT stack 2 regulation filters on the same
   category (e.g. wheelchair + large-group on attractions alone makes it trivially impossible).
2. Apply filters one at a time using `query_pool`. Count survivors after each step.
3. Check the intersection: aim for 1-3 viable venues per day per meal/sight category.
   - Zero survivors → unsolvable, relax one filter
   - 10+ survivors → too easy, add another filter
4. Confirm BOTH the restaurant side and the attraction side have at least one viable
   venue. Wiping out one category entirely = unsolvable.

### Type 6 — Context-Window Tension
1. Decide the seasonal situation: which anchor event, what it creates (closure zone,
   sold-out date, modified hours, crowd surge, weather).
2. Decide the need: what does the persona want that puts them in direct tension with
   that situation?
3. Determine scope: is this a one-time requirement (one special venue affected) or a
   whole-schedule constraint?
   - One-time: 1-3 venues should satisfy the need while avoiding the conflict.
   - Whole-schedule: 1-3 viable venues per day category after the conflict is applied.
4. Use `query_pool` + `get_venue` to check window_flags and unavailable_dates. Confirm
   the tension is real and that enough unaffected venues exist to complete the schedule.
5. Confirm the conflict is discoverable — the agent must call `get_official_site` with
   the anchor date to find it. If an agent skips that call, they should fail.

## Implementation

### New file: `scripts/generation/task_agent.py`

Contains:
- `_build_task_handbook(pool, window, city_cfg)` — dynamic handbook content
- `_dispatch_task_tool(tool_name, tool_input, pool, pool_map, window, city)` — tool dispatch
- `_query_pool(filters, pool)` — filter engine (AND logic)
- `_city_centre_from_pool(pool)` — extract from existing inline derivations in E2
- `run_task_agent(city, window, pool, type_key, model, api_key, db_path, max_turns=15,
                  unavailable=None, centre_lat=None, verbose=False) -> dict | None`

The agent loop follows the same pattern as `run_venue_agent` in `generate_venue.py`:
messages list, tool_calls dispatch, SUBMIT terminates on validation pass.

Multi-model routing: same as current `_call_single_task_llm` — Anthropic, OpenAI
(GPT + DeepSeek), Gemini all supported. Tool schemas defined per-provider format.

### Changes to `test_generate_tasks.py`

`generate_all_types()` calls `run_task_agent(...)` instead of
`build_typed_task_prompt` + `_call_single_task_llm`.

`_call_single_task_llm` stays as a sealed helper (single-shot fallback path,
activated by `--single-shot` CLI flag for testing/cost comparison).

### Changes to `generate_task.py`

`generate_task_llm()` calls `run_task_agent(...)` instead of current single-shot.
`_build_task_prompt` stays as sealed helper used by `--single-shot` path.

### SUBMIT validation

Calls existing `validate_task_schema(task, pool)` and `_verify_task_solvable(task, pool)`
imported from `test_generate_tasks.py` and `generate_task.py` respectively.
Returns structured error dict on failure so agent can read and fix.
Terminates loop on clean pass.
MAX_TURNS handles stuck agents — no separate SUBMIT retry cap.
As E3 improves `validate_task_schema`, SUBMIT validation automatically gets stronger.
