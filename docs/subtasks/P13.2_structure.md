### 1.2 What P13.2 does, in plain language

P13.2 introduces a new pure-function module `scripts/generation/scope_model.py` that builds the three pools (universal, scoped, inclusion) given a venue pool and a list of personal_constraints. It does NOT wire into any existing validator — the functions are stand-alone and unit-tested in isolation.

The helpers use the same per-venue filter logic as `_apply_pool_filters` (identical pattern handling) but split the application by `scope_mode`:
- **Universal filters** narrow the whole pool cumulatively (stage 1)
- **Scoped filters** narrow slot-specific sub-pools within the universal pool (stage 2)
- **Inclusion filters** produce candidate sets for "at-least-K" constraints (stage 3)

The functions are PURE: no I/O, no mutation of inputs, deterministic outputs. They consume already-validated P-constraints (P13.1's `_check_scope_declarations` would have been called upstream by P13.5 — but here we trust the input has valid scope_mode values).

### 1.3 Edge cases to handle explicitly

1. **Empty venue_pool** — return empty lists / dicts, not crash
2. **Empty personal_constraints** — universal_pool == venue_pool copy; scoped_pools == {}; inclusion_pools == {}
3. **All constraints are universal** — scoped_pools == {}, inclusion_pools == {}
4. **All constraints are scoped or inclusion** — universal_pool == venue_pool copy
5. **Unknown pattern** (e.g., a P-constraint with `pattern: "foobar"` that doesn't match the 6 per-venue patterns) — skip silently at the filter level (the constraint has no per-venue effect); do NOT crash. Plan-level patterns like `district_count_max` fall here.
6. **Constraint missing `scope_mode`** — in P13.2, we TRUST the input is valid (P13.1 rejects before this step). But defensively: treat missing scope_mode as an error and return early / raise. Decide in the structure doc: raise a `ValueError` with clear message. That's the "expose, not swallow" principle.
7. **Constraint missing `id`** — scoped_pools and inclusion_pools are keyed by id. Use a fallback like `f"__no_id_{idx}__"` so we don't lose the pool, but the collision risk is tiny and the fallback key is diagnostic.
8. **Duplicate constraint ids** — later overwrites earlier in dict. We could raise to be strict. Decision: raise `ValueError` — duplicate ids are a schema problem caller should have caught. This is a "silent failure to expose" case.
9. **Scoped constraint with `activity_type: "any"`** — treat as a no-op scope (any activity qualifies). So it's equivalent to applying the filter within the universal pool without scope narrowing. Edge case to handle: returns the filter applied to `universal_pool` filtered by nothing additional.
10. **Scoped constraint with `category: "restaurant,cafe"`** — parse the comma-separated string, keep venues whose `category` is in the set.
11. **Scoped with only `time_window` (no activity_type/category)** — `time_window` is plan-level context (e.g., "evening"), not a per-venue attribute. In P13.2 we can't narrow by time_window at the venue level — a venue doesn't have "evening" tagged on it. Decision: time_window scope does NOT narrow the venue-level pool; it will be consumed later in the plan-level checks (P13.5 or P9). For P13.2: ignore time_window when building scoped_pools (treat the scope as "no venue-level narrowing"). Document this explicitly.
12. **Regulations stored as flat fields vs. nested dict** — exactly as `_apply_pool_filters` handles: check `v.get("regulations")` dict first, fall back to flat `v.get(key)`.
13. **Numeric/ordinal fields (`price_tier`, `noise_level`) with unknown values** — same fallback as `_apply_pool_filters`: use sensible default ("mid" for price_tier, "moderate" for noise_level).
14. **Inclusion pattern that isn't naturally a per-venue filter** (e.g., `category_venue_count` — which P12 will introduce as a pool_filter inclusion): P13.2 handles ONLY the 6 per-venue patterns. Patterns like `category_venue_count` that use an arbitrary pool_filter dict are deferred to P12/P13.5. For P13.2, if an inclusion constraint has an unrecognized pattern, its inclusion_pool is empty — upstream should detect this.

## Part 3: Design of the new code

### 3.1 Module boundaries

`scripts/generation/scope_model.py` is a self-contained pure module. It imports:
- `PRICE_TIER_ORDER` from `scripts.generation.constraint_engine` (reuse the existing order list, don't redefine)
- Nothing else from the project

Specifically does NOT import:
- Any test file
- Any validator (test_generate_tasks.py)
- pool_utils (no circular concern with _apply_pool_filters)

Internal structure:
- Module-level constants (category groups, noise order, defaults)
- `_apply_per_venue_filter` — the private workhorse that handles the 6 patterns
- `partition_pool` — tiny utility
- `build_universal_pool` — filter loop restricted to universal-mode constraints
- `build_scoped_pools` — filter loop restricted to scoped-mode constraints, returns dict keyed by id
- `build_inclusion_pools` — filter loop restricted to inclusion-mode constraints, returns dict keyed by id

All four public functions call `_apply_per_venue_filter` under the hood. No duplication.

### 3.2 Interface design

```python
# scripts/generation/scope_model.py

"""
Scope-aware pool construction for the P13 solvability pipeline.

This module is PURE: no I/O, no mutation, deterministic output for a given
input. It consumes venue pools and P-constraints (with declared scope_mode)
and produces the three pool views used by the staged solvability checks.

P13.2 ships these helpers in isolation. P13.5 wires them into
_verify_task_solvable. Until then, nothing in the live pipeline imports
from this file.
"""
from __future__ import annotations

from scripts.generation.constraint_engine import PRICE_TIER_ORDER

# ─── Category groups ────────────────────────────────────────────────────────
FOOD_CATEGORIES = frozenset({"restaurant", "cafe", "bar"})
SITE_CATEGORIES = frozenset({"museum", "attraction", "park", "neighbourhood"})

# ─── Noise level ordering (lowest to highest) ────────────────────────────────
_NOISE_ORDER = ["quiet", "moderate", "lively", "loud"]

# ─── Per-venue filter patterns P13.2 handles ─────────────────────────────────
_FILTER_PATTERNS = frozenset({
    "label_required", "label_excluded", "regulation_required",
    "hidden_gem_required", "noise_level_max", "price_tier_required",
})


def partition_pool(pool: list) -> tuple[list, list]:
    """
    Partition a venue pool into FOOD and SITE groups based on category.

    A venue whose category is in neither FOOD_CATEGORIES nor SITE_CATEGORIES
    (rare — would indicate a new category added without updating the groups)
    is dropped from BOTH lists. Count by summing len(food) + len(site) to
    detect pool contamination; unknown categories do not silently land in
    either group.

    Returns: (food_venues, site_venues). Both are new lists.
    """
    food, site = [], []
    for v in pool:
        cat = v.get("category", "")
        if cat in FOOD_CATEGORIES:
            food.append(v)
        elif cat in SITE_CATEGORIES:
            site.append(v)
    return food, site


def build_universal_pool(
    pool: list,
    personal_constraints: list,
) -> list:
    """
    Apply all universal-mode personal_constraints to the venue pool.

    Semantics:
        universal_pool = {v in pool : v satisfies every universal constraint}

    Ignores constraints with scope_mode != "universal" (they don't narrow
    the whole pool). Patterns outside _FILTER_PATTERNS are no-ops (e.g.,
    plan-level patterns have no per-venue filter effect).

    Raises:
        ValueError if a constraint has no scope_mode field (upstream should
        have caught this; we don't silently default).
    """
    ...


def build_scoped_pools(
    universal_pool: list,
    personal_constraints: list,
) -> dict:
    """
    For each scoped-mode constraint, build its per-slot candidate pool.

    Returns dict keyed by constraint id. Each value is the list of venues
    in universal_pool that (a) satisfy the scope (activity_type/category)
    and (b) satisfy the constraint's filter.

    Scope key handling:
      - activity_type="meal" → restrict to FOOD categories
      - activity_type="site" → restrict to SITE categories
      - activity_type="any"  → no venue-level restriction (all of universal_pool)
      - category="restaurant,cafe" → restrict to those categories
      - activity_type AND category both present → intersect both restrictions
      - time_window=...    → P13.2 does NOT narrow by time_window (it's a
                             plan-level scope, not a venue attribute).
                             Scoped pool uses the other scope keys; if only
                             time_window is set, scope is treated as
                             plan-level and scoped_pool == filtered(universal_pool).

    Raises:
        ValueError if a scoped constraint has no scope_mode or no scope dict.
        ValueError on duplicate constraint ids.

    Constraints without an id use fallback key f"__noid_{idx}__".
    """
    ...


def build_inclusion_pools(
    universal_pool: list,
    personal_constraints: list,
) -> dict:
    """
    For each inclusion-mode constraint, build its candidate match set.

    Returns dict keyed by constraint id. Each value is the list of venues
    in universal_pool that match the constraint's filter criterion.

    For P13.2 we handle only per-venue filter patterns (_FILTER_PATTERNS).
    Patterns like category_venue_count (P12) use arbitrary pool_filter dicts
    and will be integrated at P13.5; P13.2's inclusion_pools for those
    patterns is empty list.

    Raises:
        ValueError on duplicate constraint ids.
    """

# ─── Private helper ──────────────────────────────────────────────────────────

def _apply_per_venue_filter(pool: list, constraint: dict) -> list:

    Pattern matching is identical to pool_utils._apply_pool_filters so the
    six filter patterns stay behaviorally consistent:
      - label_required, label_excluded
      - regulation_required
      - hidden_gem_required
      - noise_level_max
      - price_tier_required

    Unknown patterns return the input unchanged (filter has no per-venue
    effect — e.g., plan-level patterns).
    """
```

**Return-value contract:** always a new list (never a reference into the input). Pool element dicts are NOT copied (shallow only — matches `_apply_pool_filters` behavior). Callers must not mutate the venues.

**Determinism:** output list order matches input venue_pool order; dict keys are insertion-ordered by constraint appearance.

**Invariants:**
- `build_universal_pool(pool, [])` returns `list(pool)` (copy, not reference).
- `len(build_universal_pool(p, [all_universals])) ≤ len(p)`.
- `build_scoped_pools(p, [non_scoped]) == {}`.
- `build_inclusion_pools(p, [non_inclusion]) == {}`.
- `partition_pool(pool)`: `len(food) + len(site) ≤ len(pool)` (equal when every category is known).

### 3.3 Possible silent failures — exposed, not swallowed

1. **Missing scope_mode** → raise `ValueError("constraint missing scope_mode field")` with the constraint id in the message. Upstream (P13.5) should have checked first, but we don't trust silently.
2. **Invalid scope_mode value** (e.g., "UNIVERSAL") → `ValueError` with valid options listed.
3. **Duplicate constraint ids across scoped or inclusion constraints** → `ValueError`. Would otherwise silently overwrite one pool.
4. **scope_mode="scoped" but no scope dict** → `ValueError`. (P13.1 catches this in the schema validator, but we defend.)
5. **Pattern not in `_FILTER_PATTERNS`** → return input unchanged (silent no-op). This is EXPECTED behavior for plan-level patterns like `district_count_max`. Documented in the function's docstring.
6. **venue missing `tags`, `category`, etc.** → same fallbacks as `_apply_pool_filters` (empty list, empty string). These are data-quality issues upstream; filters just can't match them.
7. **Empty venue_pool** → all pool-returning functions return `[]`; dict-returning functions return `{}`. No crash.

**IN scope for P13.2:**

## Open questions — resolved by user

1. **Should P13.2 reuse the `_VALID_SCOPE_MODES` constant from P13.1's `test_generate_tasks.py`?** **RESOLVED: keep P13.2 import-free for now, BUT maintain the constant explicitly so future consolidation is easy.** scope_model.py will define its own module-level `_VALID_SCOPE_MODES` (and related constants), byte-identical to P13.1's. Both files keep their own copy intentionally. A comment in scope_model.py notes the intentional duplication and flags the consolidation path: when a third consumer appears, move both to `scripts/generation/scope_constants.py`. Until then, the near-zero cost of duplication beats the import tangle.

2. **Should `partition_pool` also be exposed as a public function used by bar checks (P13.3)?** **RESOLVED: yes.** Exposed publicly in `scope_model.py`.

3. **Should we pre-filter out non-universal constraints before passing to `_apply_per_venue_filter`?** **RESOLVED: yes.** `_apply_per_venue_filter` is scope-mode-agnostic — it just applies the pattern filter to a list. The public wrappers (`build_universal_pool`, etc.) route by scope_mode. Clean separation.

4. **Which patterns can appear in which scope modes?** Re-thought after your questions.

    **The design-level answer is simple:** every per-venue filter pattern is **scope-mode-agnostic** in the code. The helper `_apply_per_venue_filter` just applies a pattern's per-venue predicate to a list of venues. scope_mode is a routing field on the constraint that tells the OUTER builder which pool to construct. The pattern doesn't know or care what mode it's routed under.

    So from a code-structure perspective, the pattern × mode combinatorial table I drew earlier was solving a non-problem. **Test coverage only needs to verify:**
    - Each builder (`build_universal_pool`, `build_scoped_pools`, `build_inclusion_pools`) routes its mode correctly
    - The shared helper handles each of the 6 per-venue patterns correctly
    That's 3 + 6 = 9 orthogonal concerns, not 3 × 6 = 18 combinations. Dropped the pattern × mode table; I was overthinking.

    **My earlier claim about `hidden_gem_required` being "the only dual-role pattern" was wrong** — the eval handler shows several patterns support multi-mode (`regulation_required` has `at_least_one`, `label_required` has `activity_type`, etc.). But this multi-mode behavior lives in the EVAL handlers, not the filter code. P13.2's filter helper doesn't implement inclusion vs. universal differently — it just applies the pattern's match predicate. Mode is the builder's concern.

    **On `hidden_gem_required` specifically** (and why it's not folded into `label_required`):

    Looking at the actual filter code:
    ```python
    elif pattern == "hidden_gem_required":
        filtered = [v for v in filtered
                    if v.get("traffic_tier") == "low"
                    or "hidden-gem" in _tags_of(v)]
    ```
    It matches on EITHER `traffic_tier == "low"` OR `"hidden-gem"` in tags. That's a compound filter across two different venue fields. `label_required: "hidden-gem"` would only check the tag side and miss venues that are low-traffic without the explicit tag. So they're semantically distinct and the separate pattern is correct.

    **On the 6-pattern set (why noise/price but not others):**

    Your observation is sharp. Of the 6 per-venue filter patterns, `noise_level_max` and `price_tier_required` are the only ones that do ordinal comparison. The venue schema has other ordinal fields that currently have NO per-venue filter pattern:
    - `traffic_tier` (low/mid/high) — only used as part of `hidden_gem_required`'s OR, no dedicated filter
    - `recommended_pace` (relaxed/moderate/intense) — used only as plan-level `pace_relaxed`
    - `outdoor_sensitivity` (indoor/outdoor) — no filter pattern at all
    - `age_restriction`, `recommended_visit_minutes`, `avg_cost_local` — numeric, no per-venue filter

    **This is a gap in the pattern vocabulary, not a P13.2 concern.** P12 is the vocabulary-enrichment subtask; adding e.g. an `outdoor_preferred` or `pace_required` per-venue pattern would land there. P13.2 faithfully covers the 6 patterns that exist today in `_apply_pool_filters`.

    **Not captured in the 6-pattern set at all:** the 20+ OTHER evaluator handlers (`time_threshold`, `numeric_aggregate`, `district_count_max`, `cuisine_diversity_minimum`, `pace_relaxed`, `max_visit_duration`, etc.) are plan-level patterns — they evaluate whole-plan properties, not per-venue filters. For P13.2, they're silent no-ops at the `_apply_per_venue_filter` level. They'd use scope_mode in the schema (typically universal — they constrain the whole plan) but don't narrow any per-venue pool. That's fine and expected.

If these are OK, I proceed to implementation after your approval.
