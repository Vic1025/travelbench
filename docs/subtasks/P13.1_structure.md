### 1.2 What P13.1 does, in plain language

P13.1 introduces the `scope_mode` and `scope` fields to the P-constraint schema and adds validation code that checks these fields for correctness. **Critically, the validation code is NOT called from anywhere yet** — it's a built-but-dormant function. This means existing tasks continue to validate as they always have (scope_mode is just an unread field), and new tasks can start carrying scope_mode without the validator complaining. P13.5 turns on the enforcement later by wiring the dormant validator into `validate_task_schema`.

P13.1 is strictly about:
- Defining what a valid `scope_mode` / `scope` declaration looks like
- Having a standalone function that checks a P-constraint's scope declaration
- Having test coverage for that standalone function

Nothing in P13.1 changes observable behavior. It's pure infrastructure.

### 1.3 Edge cases to handle explicitly

1. **scope_mode missing** — the validation function reports this as an error. (Whether that error is actually raised in validation depends on P13.5; for now, tests verify the error is correctly identified.)
2. **scope_mode present but not in the set** `{"universal", "scoped", "inclusion"}` — error.
3. **scope_mode == "scoped" but scope field missing** — error.
4. **scope_mode == "scoped" but scope field is empty {}** — error (no actual scope declared).
5. **scope_mode == "scoped" but scope has irrelevant keys** (e.g., `{"foo": "bar"}`) — error.
6. **scope_mode == "scoped" and scope has valid keys** (`activity_type`, `category`, `time_window`) — pass.
7. **scope_mode == "scoped" and scope.category has values not in the known categories list** — error.
8. **scope_mode == "scoped" and scope.activity_type has an unknown value** — error.
9. **scope_mode == "inclusion" but constraint has no `min_count` param** — error (inclusion requires min_count).
10. **scope_mode == "universal" but scope field is present** — warning, not error (field is redundant but not broken).
11. **Multiple values separated by comma** in scope.category (e.g., `"restaurant,cafe"`) — parse correctly, validate each value.
12. **Whitespace in scope values** — trim before validating.
13. **scope field is not a dict** (e.g., scope is a string) — error with clear message.
14. **P-constraint is a B-score rather than personal_constraint** — skip; scope_mode only applies to personal_constraints.

### 1.4 What "done" looks like

- A standalone function `_check_scope_declarations(personal_constraints)` exists and returns a list of violation strings (empty = OK).
- New tests in `scripts/generation/test_e3.py` cover each edge case above.
- The function is NOT called from `validate_task_schema` yet (that happens in P13.5).
- All existing tests still pass (429/429).
- New tests pass.
- Schema structure is documented (either in code comments or an updated P13_scope_model.md note).

### 1.5 What the user would see change

After P13.1 alone: nothing observable. Schema validation behaves identically to today. Agent-generated tasks still pass. Existing 60 tasks still pass.

The change is ONLY visible internally to someone running the new function directly, which would be P13.5 or a test.

## Part 3: Design of the new code

### 3.1 Module boundaries

All of P13.1 sits in `test_generate_tasks.py`. One new function, one constants block. No new file. No new import dependencies.

Rationale: This sub-subtask produces ~40 lines of code. A new module for this would be overkill and add import overhead to other files that consume the constants. Schema validation lives in `test_generate_tasks.py` historically; keeping it there preserves that convention.

Later sub-subtasks (P13.2, P13.3, P13.4) will produce the `scope_model.py` module. P13.1 intentionally does NOT introduce it.

### 3.2 Interface design

```python

_VALID_SCOPE_KEYS = frozenset({"activity_type", "category", "time_window"})

    Validate scope_mode + scope fields on each personal_constraint.

    Returns a list of issue strings. Empty list = all valid.

    Does NOT assign default scope_modes — agents must declare explicitly.
    This function only *checks*; it never mutates constraints.

    Per P13 design: scope_mode is required on all P-constraints.
    - "universal": no scope field needed (or scope field is None/absent)
    - "scoped":    scope field required with activity_type or category or time_window
    - "inclusion": min_count required in params; scope field not used

    Silent failures to avoid:
    - Do NOT fall back to a default scope_mode if missing — error out
    - Do NOT accept scope_mode "scope" or "Universal" — strict set membership
    - Do NOT accept scope with unknown keys — they're either a typo or misuse
    """

```

**Return contract:** a list of strings. Each string is a human-readable error message with the constraint's `id` prefixed where possible (e.g., `"[pc_001] scope_mode missing"`). Consistent with how `validate_task_schema` already reports issues.

**Side effects:** none. Pure function.

**Invariants:**
- Input is a list (may be empty).
- Each element is a dict (may lack expected fields — the function handles missing fields gracefully).
- Output is always a list of strings.
- Output is deterministic given the same input (no random ordering).

### 3.3 Possible silent failures — exposed, not swallowed

1. **scope_mode is an empty string `""`** — this is not `None` but also not valid. Will fail the set-membership check. Good.
2. **scope is `None` but scope_mode is "scoped"** — error. Good.
3. **scope_mode case sensitivity** — "Universal" vs "universal". Strict equality, so "Universal" fails. Good (matches the hard-require principle).
4. **`min_count` missing for inclusion mode** — error. Good.
5. **`min_count` is 0 or negative** — error. Good (need at least min_count >= 1).
6. **Multiple scope keys set simultaneously** (e.g., both activity_type AND category) — ALLOWED. The intent might be "dinner AT restaurants" which is legitimately both. Document this in the docstring.
7. **Constraint is missing the `id` field entirely** — error message uses "[?]" as id placeholder. Matches existing error formatting.
